# Design

## Context

動機は proposal.md を参照する。現状の実装は次の比較と設定検証を行う。

- `internal/relay/server.go:150` はtargetと `Config.PublicURL` を文字列比較する。
- `internal/relay/server.go:154-157` はsourceのfragmentを除去し、`u.String() == target` で自己を判定する。
- `internal/relay/parse.go:101` は `base.ResolveReference(u).String() == target` でリンクを比較する。
- `internal/relay/config.go:24` は空パスと `/` を既に受理する。
- `internal/relay/config.go:25` は「末尾 /」を要求する誤ったエラー文を返す。
- `.env.example` は末尾 `/` の例を示す。`internal/relay/retry_test.go:31-34` は空パスの受理を確認する。

`net/url` は空パスと `/` を区別する。一方、既存のURL解析は空の `#` を保持しない。既存の設定検証はその入力も受理する。解決済みリンクの直列化結果は、失った元表記を復元しない。

SQLiteはsource単独の一意制約で投稿を固定する。リレーは任意sourceの入力文字列を識別子として扱う。

## Goals / Non-Goals

**Goals:**

- 開発者は受付、自己判定、解決済みリンク比較に同じルート規則を使う。
- 開発者は比較用URLと保存用source文字列を分離する。
- リレーは既存の設定受理範囲とデータ保存契約を維持する。

**Non-Goals:**

- 開発者は空の `#` 付き設定の新規拒否を別変更へ延期する。
- 開発者はホスト大小文字、既定ポート、エンコード表記の独自同値規則を追加しない。
- 開発者は非ルートの `/post` と `/post/` を同値化しない。
- 開発者は解析・参照解決・直列化で失った元表記の拒否検査を追加しない。
- 開発者はsource識別子の正規化とデータベースの書換えを行わない。

## Decisions

### 決定: 解析済みURLのルート空パスだけを揃える

開発者は `internal/relay` に比較用ヘルパーを置く。ヘルパーはHTTP(S)ルートURLのコピーを作り、空の `Path` だけを `/` にする。ヘルパーは他のパスとURLフィールドを変更しない。

比較は既存の `net/url` の解析結果と `URL.String()` の直列化を使う。ヘルパーはスキーム、ホスト、ポート、認証情報、query、`ForceQuery`、fragment、`RawPath` を保持する。開発者は既存の解析・直列化に独自の同値規則を重ねない。

代替案は `strings.TrimRight` による末尾スラッシュの一括除去である。この案は非ルートパスの意味を壊す。開発者は空パスだけの変更を選ぶ。

### 決定: 設定の解析と検証条件を維持する

開発者は `config.Validate` の既存の解析と検証条件を変更しない。開発者はエラー文だけを実際の受理条件に合わせる。設定検証はquery、`ForceQuery`、非空fragment、認証情報、非ルートなどの既存制約を維持する。

代替案は元文字列の空の `#` を検査する新しい設定拒否である。この案は外部から見える互換性を変更する。開発者はこの硬化を本変更に含めない。

### 決定: 受付と自己判定に共有比較を使う

受付は通知targetと設定ルートを解析し、共有ヘルパーで比較する。比較結果が異なる場合、受付はHTTP 400を返す。受付はqueryや非空fragmentを除去してtargetを一致させない。

受付は既存の `sourceURL` 検査を維持する。受付は自己比較用のURLコピーからfragmentを除去し、共有ヘルパーで照合する。受付はsourceの元文字列を取得と保存へ渡す。

自己判定は両ルート表記とfragment付き自己sourceを拒否する。自己判定はquery付きsourceや非ルートsourceをルートと同値化しない。

代替案は各呼び出し箇所に表記別の条件を追加する案である。この案は三箇所の比較規則を分散する。開発者は共有比較を選ぶ。

### 決定: 新規targetだけを末尾 `/` の内部表現で保存する

受付は共有ヘルパーの比較用ルート表現を新規jobのtargetへ渡す。リレーは設定URLの入力表記とsource入力を変更しない。リレーは既存jobのtargetを比較時に扱い、保存列を書換えない。

代替案は新規targetも入力表記のまま保存する案である。開発者は新規jobの表現を揃えるため、末尾 `/` の表現を選ぶ。既存jobからの初回保存は、そのjobのtarget表記を保持する。

### 決定: 原本リンクは参照解決後の表現で判定する

`parse.go` は最終取得URLと最初の `base href` による既存の参照解決を維持する。パーサーは `ResolveReference` 後のURLとjobのtargetを共有ヘルパーで比較する。パーサーは既存jobの空パス表記も扱う。

拒否条件は解決後にも残る差に適用する。パーサーは元リンク表記の拒否を保証しない。特に、既存の解析は空の `#` を既に失う。

代替案は元のHTML属性を追加検査する案である。この案は既存の参照解決による受理結果を変える。開発者はその検査を導入しない。

## Risks / Trade-offs

- [解析と直列化が元表記を失う] → 開発者は解決後の表現を検証し、元表記の拒否を保証しない。
- [設定が空の `#` を受理する] → 開発者は既存の受理範囲を維持し、新規拒否を別変更へ延期する。
- [新旧jobのtarget表記が混在する] → リレーは共有比較で両表記を扱い、既存列を書換えない。
- [広い正規化が別資源を同値化する] → 開発者は空パスだけを変更し、残るhost・scheme・path・query・fragmentの差を回帰テストで確認する。

## Migration Plan

- 運用者は更新前にリレーを停止する。
- 運用者は保存ディレクトリ全体をバックアップする。
- 運用者は同じ設定と保存先で新バイナリを起動する。
- リレーは両target表記の未処理jobと中断jobを、既存の復旧規則で処理する。
- リレーは既存job、既存投稿、source識別子、SQLiteスキーマを一括書換えしない。
- リレーは過去のfailed jobを自動復活させない。送信者は修正後に未保存sourceを再通知する。
- ロールバック時、運用者はリレーを停止して旧バイナリへ戻す。
- 旧バイナリは同じスキーマを読む。ただし旧比較のルート表記依存は再発する。
- 運用者はロールバック後の受付と未処理通知を確認する。データベースの逆移行は不要とする。
