# Tasks

各グループは独立した検証単位とする。実装者はその単位の検証後にだけチェックを付ける。テストは実記事ではなく固定fixtureを使う。テスト専用の内部IP許可を本番設定へ持ち込まない。

## 1. アプリ基盤と依存

- [ ] 1.1 Goモジュール、実行入口、取得・解析・保存・配信の境界を作る — verify: 固定したGo環境で `go build ./...` が成功する。
- [ ] 1.2 mf2、safeurl、Atom、UUIDの依存を固定し、ライセンス情報を記録する — verify: `go mod verify` が成功し、go.modとgo.sumと依存一覧が一致する。
- [ ] 1.3 SQLiteドライバー候補を導入し、最小のファイル保存テストを追加する — verify: `CGO_ENABLED=0 go build ./...` とDBの書き込み・再接続テストが成功する。

## 2. 安全な取得

- [ ] 2.1 safeurlの本番取得層と設定検査を実装する — verify: HTTP/HTTPS、許可ポート、認証情報、IPv4/IPv6内部IP、内部IPへ解決するホスト名の許否テストが成功する。
- [ ] 2.2 全転送先のCheckRedirectと環境プロキシ無効化を実装する — verify: 内部IP、認証情報付きLocation、非HTTP転送、回数超過、proxy環境の試験で拒否先へのHTTP到達がゼロになる。
- [ ] 2.3 時間と展開後本文サイズの制限を実装する — verify: 遅いヘッダー、遅い本文、gzip、長さ不明の本文の上限テストが成功する。
- [ ] 2.4 DNS変化の回帰テストと取得設定の説明を追加する — verify: 新規接続の許可IPから拒否IPへの変化を拒否し、`go test -race` が成功する。本番とテストの検査範囲を文書に記す。

## 3. リンク検証とmf2

- [ ] 3.1 同じ取得済みHTMLのリンク検証とmf2解析を実装する — verify: 相対リンク、base、リダイレクト、Webmention対象属性、リンク欠落のfixtureが成功し、補助URLの外部取得がゼロになる。
- [ ] 3.2 UUID URNと単一h-entry・単一collectionの検査を実装する — verify: 不正URN、大小文字、重複宣言、複数所属、h-feed内の複数投稿、不正宣言混在のfixtureが成功する。
- [ ] 3.3 入れ子のHTML除去と安定したmf2 JSON表現を実装する — verify: h-cardとchildrenの構造、content.value、全階層のHTML除去、JSON往復、同値ハッシュのテストが成功する。
- [ ] 3.4 投稿者向けの最小ページ例と入力制約を文書化する — verify: 文書内のページ例を同じパーサーで検査し、単一投稿・単一所属として受理する。

## 4. 永続ストアと処理状態

- [ ] 4.1 collections、posts、jobsのスキーマと初期化を実装する — verify: 初回作成、再接続、スキーマ版不整合、書き込み不能、一意制約のDBテストが成功する。
- [ ] 4.2 掲載・更新・所属変更・撤回をトランザクションで実装する — verify: 同じ通知の重複、同値再通知の日時、旧所属からの移動、空collectionの保持、ロールバックのDBテストが成功する。
- [ ] 4.3 キュー上限、source単位の直列化、中断復旧、有限の再試行とjob削除を実装する — verify: 同時通知、worker中断後の再起動、再試行上限、保持期限のDBテストが成功する。
- [ ] 4.4 データ境界と復旧・再試行の挙動を文書化する — verify: DBの読み戻しがHTMLなしのmf2と一致し、文書の復旧例をテストで確認する。

## 5. HTTP受付と処理接続

- [ ] 5.1 ルート説明、Webmention広告、POSTフォーム検査、永続受付を実装する — verify: LinkヘッダーとHTML広告、202、400、メソッド拒否、フォーム上限、満杯時503、保存失敗時の非202をHTTPテストで確認する。
- [ ] 5.2 workerを取得・解析・ストアへ接続し、撤回と一時失敗を区別する — verify: 新規、編集、所属移動、404/410、リンク消失、資格消失、5xx、タイムアウト、安全拒否、サイズ超過の処理テストが成功する。
- [ ] 5.3 PUBLIC_URL、資源上限、HTTPサーバーの有限タイムアウトと停止処理を実装する — verify: 不正設定の起動拒否、Hostから独立したtarget、有限worker数、正常停止のテストが成功する。
- [ ] 5.4 通知コマンドと更新・削除の制約を文書化する — verify: 文書のフォーム送信を固定sourceサーバーへ実行し、受付と掲載を区別する。

## 6. Atom配信

- [ ] 6.1 保存済みmf2からAtom専用型への出力を実装する — verify: collection URN、source entry id、self、textコンテンツ、XMLエスケープ、タイトル・著者・日時の代替値をXML解析テストで確認する。
- [ ] 6.2 feed経路、順序、件数上限、未知・空collectionを実装する — verify: Content-Type、404、空feedの200、安定した順序とupdated、同じsourceの別リレー識別子をHTTPテストで確認する。
- [ ] 6.3 feedのURL、投稿識別子、メタデータ、段落境界の制約を文書化する — verify: 文書の購読URLを取得し、出力と文書が一致する。

## 7. 単一コンテナ運用

- [ ] 7.1 非rootのDockerfile、永続ボリューム、ヘルス確認を実装する — verify: `docker build` と単一コンテナ起動が成功し、UIDが非rootで、healthは保存先とworkerの異常を反映する。
- [ ] 7.2 起動・再作成・バックアップ・復元の運用説明を追加する — verify: 文書のコマンドを実行し、同じボリュームの投稿と受付済み通知が再作成後に残る。

## 8. 統合確認

- [ ] 8.1 Webmention受付からSQLite保存とAtom配信までのE2Eを実行する — verify: 固定sourceで新規、同値再送、編集、所属移動、撤回、空feed、一時障害を確認する。本番のSSRF制約を緩めず、テスト用取得層を明示する。
- [ ] 8.2 コンテナ停止・再作成を含むE2Eを実行する — verify: 掲載前の通知が再処理され、既存投稿のidとmf2が保持され、重複がない。
- [ ] 8.3 全体の静的検査・競合検査・OpenSpec検証を実行する — verify: `go vet ./...`、`go test -race ./...`、`openspec validate build-public-collection-relay --strict` が成功する。実行不能な検査は未完了のまま報告する。
- [ ] 8.4 Webmention相互運用と最終成果物を確認する — verify: 仕様由来の受信ケースと利用可能な相互運用試験の結果を記録し、起動コマンド、依存、仕様、Dockerの結果が一致する。
