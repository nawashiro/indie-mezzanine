# Design

## Context

動機は`proposal.md`の`Why`を参照する。外部契約は`specs/webmention-ingestion/spec.md`を参照する。

現行実装は、次の状態を持つ。

- `internal/relay/store.go:72-97`の`Enqueue`は、`posts`だけを重複判定に使う。
- 同関数は、`pending`と`running`の件数を容量として数える。空きがあると同関数は常にjobを挿入する。
- `Claim`は、同じsourceの並列実行を防ぐ。`Claim`は、既存の重複jobの順次実行を防がない。
- `Process`は、保存済みsourceの取得を省略する。初回失敗時は、後続の重複jobが再取得を起こす。
- `OpenStore`は、`SetMaxOpenConns(1)`で接続数を一つに制限する。
- `Finish`は、成功を`done`、終端失敗を`failed`、有限再試行を`pending`として記録する。
- `Recover`は、中断した`running`を`pending`または`failed`へ戻す。
- `Cleanup`は、古い終端jobと古い`pending`を削除する。

現行テストは、次の期待値を持つ。

- `TestQueue`は、同じsourceの同時通知から三件のjobを受け付ける。
- `TestHTTPAdmission`は、容量一のキューで同じsourceの二回目の通知へ503を期待する。
- `TestE2EAndRestart`は、初回失敗後の通知と保存後の再通知を検証する。
- `TestConcurrentFirstSnapshot`は、投稿のsource単独の一意性を検証する。

主仕様の「キューの容量超過」は、処理待ち重複にも503を要求する。本差分は、条件をスナップショットも処理待ちjobもないsourceへ限定する。

## Goals / Non-Goals

**Goals:**

- ストアは、同じsourceの受付競合を一つの永続jobへ収束させる。
- ストアは、保存済み判定、処理待ち判定、容量判定、挿入を同じトランザクションへ置く。
- HTTP受付は、新規受付、処理待ち再通知、保存済み再通知を区別する。
- テストは、job件数と取得回数を別々に検証する。

**Non-Goals:**

- 本変更は、source URLの正規化やtarget URLの正規化を追加しない。
- 本変更は、再通知によるtarget差し替えや取得予定の前倒しを行わない。
- 本変更は、有限再試行、中断復旧、保持期限を変更しない。
- 本変更は、複数プロセスや複数の`Store`による同時書き込みを対応範囲へ加えない。
- 本変更は、旧実装が作った重複jobの統合移行を行わない。

## Decisions

### 1. source単独で処理待ち重複を確認する

`Enqueue`は、保存済み判定の直後に、同じsourceの`pending`または`running`の存在を確認する。検索は、既存の`jobs_source(source,state)`索引を利用する。

`posts`の存在は、処理待ちjobより優先する。保存直後かつ`Finish`前の再通知も、従来の`ErrStored`とHTTP 200へ収束する。

ストアは、source文字列の完全一致だけを使う。source単独の保存キーと、受付の冪等キーが一致する。

公開受付は、重複判定より先にフォームとtargetを検証する。設定済みtarget以外の通知は、既存jobの有無にかかわらず400を返す。

ストアへ異なるtargetで同じsourceを渡した場合も、ストアは既存jobを変更しない。既存jobは、最初の永続受付時のtargetで処理を続ける。

代替案の`(source,target)`キーは、同じsourceに追加jobを作る。代替案のtarget上書きは、実行中の検証対象を曖昧にする。設計は両案を採用しない。

### 2. 容量判定の前に重複結果を返す

`Enqueue`の結果は、次の優先順位を持つ。

| 条件 | ストア結果 | HTTP応答 | jobへの作用 |
| --- | --- | --- | --- |
| `posts`が存在する | `ErrStored` | 200 | ストアは変更しない |
| `pending`または`running`が存在する | 新しい`ErrOutstanding` | 202 | ストアは変更しない |
| 処理待ち件数が上限へ達する | `ErrFull` | 503 | ストアは追加しない |
| 上記以外 | 挿入とコミット成功を表す`nil` | 202 | ストアは一件追加する |
| 永続ストアの操作が失敗する | 操作エラー | 503 | 受付は成功を示さない |

`ErrOutstanding`は、既存の永続処理待ちjobを確認した結果を表す。ストアは、確認トランザクションのコミット成功後だけ、この結果を返す。

HTTP受付は、この結果へ専用の本文を返す。本文例は「通知は永続受付済みです。既存の処理を継続します。掲載は原本検証後です。」とする。

HTTP 202は、未完了の検証処理の受付を示す。HTTP 200は、従来の保存済みスナップショット保持を示す。両応答は、Webmentionの成功応答と受付・掲載の区別を維持する。

代替案のHTTP 200は、処理待ちと保存済みの応答を同一にする。代替案の`nil`だけの返却は、追加jobを作らない専用本文の選択を難しくする。設計は専用結果と202を採用する。

### 3. 既存のトランザクションと単一接続で競合を直列化する

ストアは、重複確認を`Enqueue`の既存トランザクション内へ置く。ストアは、確認前にトランザクションを終了しない。

一つの`Store`では、接続数一の制約が受付、claim、保存、完了、削除の操作を直列化する。後続の受付は、先行受付のコミット後のjobを読む。

`Apply`が先にコミットすると、受付は保存済みとして返す。受付が先に進むと、受付は既存の処理待ちjobへ集約する。

`Finish`が先に終端失敗を確定すると、受付は通常の新規挿入へ進む。受付が先に進むと、受付は既存jobへ集約する。後者の通知は、将来の成功や失敗後の新規再試行を保証しない。

`Cleanup`が先にjobを削除すると、受付は削除後の状態で容量を確認する。受付が先に進むと、受付は確認時点の永続jobへ集約する。受付は、既存の保持期限を延長しない。

代替案のメモリ上の重複表は、再起動で根拠を失う。代替案の部分一意索引は、旧jobの重複解消とスキーマ移行を要求する。現行の単一ストア構成では、設計は両案を追加しない。

### 4. 終端履歴と処理待ちjobを分離する

重複確認は、`done`と`failed`を含めない。スナップショットがない場合は、これらの履歴を残したまま新規jobを作る。

`failed`後の通知は、容量があれば試行回数ゼロの新しいjobを得る。容量がなければ受付は503を返す。履歴の存在は、受付成功の根拠にならない。

保存済みsourceは、jobの状態や履歴削除にかかわらず`ErrStored`へ収束する。有限再試行と復旧による取得は、重複通知が追加する取得とは区別する。

代替案の全履歴による重複判定は、初回失敗を永久拒否へ変える。設計はこの案を採用しない。

### 5. 件数、状態、取得回数を分けて検証する

テストは、次の観測を使う。

- ストアテストは、同じsourceの同時受付後のjob件数を一として検証する。
- 容量テストは、異なるsourceで上限を埋める。重複受付の成功数と容量消費を混同しない。
- 重複テストは、`pending`と`running`の両状態を検証する。
- 境界テストは、満杯と残り一枠で重複を送る。後者は、別sourceの受付成功も確認する。
- 状態テストは、target、状態、試行回数、`next_at`、`created`の不変性を確認する。
- 処理テストは、重複通知後の取得回数と後続claimの不在を確認する。
- 初回終端失敗の処理テストは、スナップショットがなくても余分な取得が発生しないことを確認する。
- 再通知テストは、終端失敗後の新規jobを確認する。
- 保存済みテストは、保存直後かつjob完了前も200、追加jobなし、再取得なしを確認する。
- 保持期限テストは、削除後の新規受付と再試行待ちの期限不変を確認する。

実行中のテストは、同期用チャネルで取得開始と終了を制御する。取得回数の観測は、mutexなどで同期する。テストは、既存の非同期未対応`countFetcher`を並列workerへそのまま渡さない。

## Risks / Trade-offs

- [単一接続の前提を将来の変更が崩す] → 設計と競合テストは前提を明示する。複数接続への変更は、別途原子的な受付方式を要求する。
- [旧実装の重複jobが残る] → 新受付は行を増やさない。旧jobは従来の順次処理と期限削除を続ける。
- [旧重複jobが一時的に容量と取得を消費する] → 本変更は既存jobの集約を保証しない。旧データの統合移行は別変更として扱う。
- [202を掲載成功と誤解する] → 処理待ち専用本文は、既存処理の継続と検証前の状態を示す。
- [再通知が直後の失敗や期限削除を防ぐと誤解する] → 再通知は試行回数と受付時刻を変更しない。既存ライフサイクルが終了を決める。
- [同じsourceの異なるtargetが無視される] → 公開受付は設定外targetを拒否する。ストアは最初のtargetを保持する。
- [複数sourceが異なるURL表記で同じ資源を指す] → 本変更は既存のsource文字列の同一性を維持する。URL正規化は範囲外とする。

## Migration Plan

- 実装者は、スキーマ版2と既存索引を維持する。
- 運用者は、通常のコンテナ更新で本変更を配備する。
- 新受付は、旧jobの存在を重複確認に使う。新受付は、旧jobのtargetや状態を変更しない。
- 運用者は、旧バージョンへの更新でロールバックする。ロールバックは、同じ保存先を維持する。
- 旧実装は、ロールバック後に重複jobを再び追加する。本変更は、ロールバック先の重複受付を保証しない。
